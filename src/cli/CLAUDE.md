# CLAUDE.md (CLI)

## `publish-content` flow

1. If `--overwrite-existing` and `--local` are not set, list the `<publishId>_files_sha256_` keys one time. The KV Store list uses `consistency=strong`. `getStorageKeysByHexPrefix()` runs 16 listings at the same time, one for each hex digit after the prefix, because a listing gets its pages one after another (about 0.36 s for each 1,000 keys on S3 in a test).
2. Scan the files with `concurrentMap()`, at most 16 at a time (or the CPU count, if it is less). For each variant: if its key is in the list, skip the variant. Do not compress, hash, or upload it.
   - For a chunked original, all keys `_1`, `_2`, … must be in the list. `isVariantInStorage()` also gets the stored size of each chunk (one `HEAD` for each chunk; the KV Store API gives `stored-content-length`). It removes a chunk with a different size from `existingKeys`, so that `applyBatch()` uploads it again.
   - Skip a compressed variant only if the original fits in one chunk. The chunk count of a compressed variant is not known before compression.
3. Upload a compressed variant only if it is smaller than the original. Thus, if a compressed variant is in storage, the index keeps it. Variants that are not smaller are compressed again at each publish. Most of these are very small files.
   - Compression uses async zlib, so it runs in parallel on the libuv thread pool. `src/cli/index.ts` sets `UV_THREADPOOL_SIZE` (4 to 16, from the CPU count) if it is not set. Do not use the `*Sync` zlib functions: they block the event loop, so files are compressed one at a time.
   - `brotliQuality` in `publish-content.config.js` sets the brotli quality (default 11, the slowest). `--brotli-quality` overrides it. If neither is set, the output is the same as the zlib default.
4. `applyBatch(batch, { existingKeys })`:
   - The KV provider splits files that are larger than 20 MiB into chunks (S3 does not use chunks). It writes each chunk file with `pipeline()`, which resolves after the file is completely written. The upload reads the chunk files. It removes the chunks that are in storage. Then it uploads NDJSON batches of at most 256 items / 8 MiB. Larger entries use one PUT each.
   - The S3 provider uploads one `PutObject` for each entry, 64 at a time by default (`--s3-upload-concurrency`). The S3 client gets an HTTP agent with enough sockets for this; the SDK default is 50.
5. The CLI writes the index and the settings only after all uploads are successful.

The log lines for each file (scan) and each upload go through `ProgressLog` (`util/progress.ts`). Without `--verbose`, it logs only a progress line after each 1,000 items, because a large site has tens of thousands of files.

`src/cli/storage/CLAUDE.md` has the measured limits of the KV batch endpoint.

## Generating the app

`generateApp(config)` (`src/cli/commands/scaffold/generate-app.ts`) makes all files of a scaffolded app as a map from path to content. It does not write files or use the network. It reads only `resources/`:

- `resources/templates/<name>/`: a template. Its files (for example `src/index.js`) are copied into the app as they are. Its `package.json` and `package-lock.json` are not app files: `generateApp()` reads the dependencies from the `package.json`. Dependabot keeps both files up to date (`.github/dependabot.yml`). To change a dependency by hand, edit the `package.json` and run `npm install --package-lock-only --ignore-scripts` in the template directory, with npm 11 (Node.js 24), as CI does. Another npm version can write a different lockfile, and then the check of CI fails. The template `package.json` has no `scripts` and does not list this package, so that `npm install --package-lock-only --ignore-scripts` in the template directory runs nothing. CI checks that each lockfile matches its `package.json`. `app-template.ts` lists the valid template names. The entry file of the app is `"main"` in the template `package.json` (default `src/index.js`; `hono` has `src/index.ts`), and `generateApp()` puts it in the `build` script. js-compute's esbuild builds a `.ts` entry by removing the types; nothing in the build runs `tsc`. To type-check a test app, install this package from `npm pack`: a `file:` link to the checkout gives TypeScript the checkout's own dev copy of `hono`, so `hono`'s types do not match.
- `resources/app/*.njk`: `fastly.toml`, `static-publish.rc.js`, `publish-content.config.js`, and `.gitignore`, rendered with Nunjucks (`render.ts`). Autoescape is off. Each `{{ … }}` must use one of the filters `js`, `toml`, `tomlKey`, or `line`, which write the value in the syntax of the file. A unit test checks this.

A template never has a file that `generateApp()` writes itself; `generateApp()` throws if it does. `scaffold` resolves the flags into an `AppConfig` (also the S3 endpoint lookup), calls it, writes the files, and runs `npm install`.

`test/unit/generate-app.test.js` compares its output with the golden files in `test/golden/<case>/`, and `test/e2e/scaffold-golden.test.js` checks that `scaffold` writes the same files. A change that must not change the generated app must not change a golden file. After an intended change, run `UPDATE_GOLDEN=1 npm test` and check the diff of `test/golden/`. The golden copy of a `.gitignore` is named `_gitignore`, because git would obey a real one in the tree. The dependency on this package is the placeholder `<compute-js-static-publish>`, and the version and the date in `generatedFrom` are `<static-publish-version>` and `<generated-at>`.

## Before the mode is detected

`src/cli/index.ts` handles these before it detects the mode:

- `run-template-hook <name>`: the template hooks call it. It prints no banner, and works in any directory.
- `run-dev-watch [<options>]`: the `dev:watch` script of an app calls it. It runs `fastly compute serve --watch` with the options, and `scripts/template_watch.js` next to it if the app has that file. It prints no banner, and works in any directory.
- `--version`: prints only the version.
- `--json`: `parseGlobalOptions()` removes it with the other global options. See "CLI output contract" below.
- `--project-dir`: the CLI checks that the directory has `static-publish.rc.js` or `static-publish.project.js`, then runs `process.chdir()` into it. Thus every relative path, also the paths in the options, is relative to the project dir. `parseGlobalOptions()` removes these options from `process.argv` before the commands parse it.

## CLI output contract (for CI)

`src/cli/util/output.ts` has the contract with tools that run the CLI: the exit codes (`0` success, `1` the operation failed, `2` a usage or config error), the `--json` output (one object on stdout at the end, `schemaVersion: 1`; with `--json`, every console method writes to stderr), and the error codes (`CliErrorCode`). The exit code comes from the error code (`exitCodeOf()`). The README lists each code with its exit code, and a unit test checks that list, so a new code needs a README row. A new code can come in a minor release; to rename or remove a code, or to change its exit code, is a breaking change.

A command never sets `process.exitCode` itself. It calls `fail(code, message)` (shows `❌ message` and fails), or `recordFailure(code, message)` when the log already shows the error. With `--json`, the output has the first error. `setJsonResult()` sets the result. `src/cli/index.ts` writes the JSON object after the command, and an uncaught error gives `failed` (exit `1`), or `config-invalid` (exit `2`) for a `ConfigError` (`util/output.ts`). Throw a `ConfigError` for an error in the settings that a command finds after it loads them, for example in `generateApp()`. `manage/index.ts` and `collections/index.ts` refuse `--json` (`json-not-supported`) for the commands that do not support it: only `publish-content`, `collections list`, `collections delete`, `collections promote`, `status`, `deploy`, and `--version` do. A child process that writes to stdout (the Fastly CLI, `npm ci`) gets stderr as its stdout with `--json`.

## Managed projects

A managed project has one file, `static-publish.project.js` (`models/config/static-publish-project.ts`), in the project dir. The name marks the mode (`detectProjectMode()` in `cli/util/config.ts`: project file → managed, rc → ejected, neither → scaffold, both → error). `loadStaticPublisherRcFile()` returns its top level, and `loadPublishContentConfig()` its `publishContent` (unless `--config`). `scaffold --managed` builds the same `AppConfig` as an ejected scaffold and writes it with `renderProjectFile()` (`cli/managed/project-file.ts`, from `resources/app/static-publish.project.js.njk`); `appConfigFromProject()` gives the same `AppConfig` back (a unit test checks this round trip for each golden case). The generated app goes into `.static-publish/app/`, and its rc has no `generatedFrom`. The line `    serviceId: undefined,` in the `managed` section is the marked line that `deploy` replaces. `staticPublisherWorkingDir` follows `checkStaticPublisherWorkingDir()` (`./` or `../`, not the config dir or above it) in both modes.

`managed.fastlyToml` (`commands/scaffold/fastly-toml-sections.ts`): `generateApp()` appends its `local_server` and `setup` tables to the `fastly.toml` that the template renders. Each table header has the full path, so that no table of the CLI is declared a second time; a name that the CLI writes, or values in a table that the CLI writes, are errors, and the result is parsed again to check it. `managedAppState()` computes the fingerprint without `local_server`.

The generated app of a managed project (`cli/managed/app.ts`): `managedAppConfig()` adds `packageLock`, the template's lockfile (`resources/templates/<name>/package-lock.json`) plus the `file:` link entries to the running CLI's package dir (`buildManagedLockfile()`, `cli/managed/lockfile.ts`). `writeManagedAppFiles()` never deletes a file, so after a change of `managed.template` the files of the old template stay in the app dir (the build uses the entry file of the new template, and the fingerprint uses the generated files). It writes a file outside the app dir (the working dir's `kvstore.json`) only if it is missing. `npm ci` runs only when the hash of `package.json` and `package-lock.json` differs from the stamp in `node_modules/`. In a managed project, `getComputeAppDir()` is `.static-publish/app`, because the local KV Store file has paths relative to the dir where `fastly compute serve` runs.

`deploy`/`status` (`cli/managed/fingerprint.ts`): the fingerprint is a SHA-256 of `managedAppFiles()` (`generateApp()` without `publish-content.config.js`), with the CLI's paths replaced, the `service_id` line of `fastly.toml` and `generatedFrom` removed, plus the version and the template. The version comment is `static-publish <version> fp:<sha256>[ | <text of --comment>]` (`parseVersionComment()`); `status` and `deploy` read it from the active version (`GET /service/<id>/details`). Write-backs into the project file (`project-edit.ts`) replace one known line only. The version check (`version-check.ts`, semver order) runs in `dev` and `deploy`.

`eject` (`commands/manage/eject.ts`, `managed/eject.ts`) works on the loaded project, not on its source text: `publishContent` must be data (`findNonDataPaths()`). If it equals what `scaffold --managed` writes, eject writes the same `publish-content.config.js` as an ejected scaffold (an e2e test compares an ejected project with an ejected scaffold of the same flags); else a literal. It pins this package with `npm install --save-prod <pkg>@<version>` (a dependency of the app), which needs a published version; the tests set `CJSP_TEST_ONLY_EJECT_PACKAGE_SPEC` to a `file:` spec.

## Hono extensions

The `hono` template loads the modules of an extensions folder (`build.hono.extensionsDir`, default `./hono-extensions`, relative to the project file or the rc). The settings of a template are in `models/config/template-settings.ts` (`TEMPLATE_SETTINGS`, `checkTemplateSettings()`): `build.<template>` and `templateOptions.<template>`. `normalizeStaticPublisherRc()` keeps them; an unknown key is a warning, and an invalid value is an error. A managed app gets only the `templateOptions` key of its template.

- `src/cli/hono/build.ts` is the public export `./hono/build`, for the scripts of the template, which stay in an ejected app. `bundleHonoExtensions()` (the `prebuild` hook) bundles the modules with the esbuild of the app (the script passes it, because this package can be a `file:` link to a directory without esbuild) into `src/hono-extensions.generated.js` (gitignored). The dependencies of the app, this package, and `fastly:*` are external (`honoExtensionsExternals()`), so the app has one copy of each. It writes the file only if its content changes. `watchHonoExtensions()` (`scripts/template_watch.js`, which `run-dev-watch` and `dev -- --watch` start) watches the folder (or its parent until the folder exists) and bundles again after a change. The Fastly CLI watches only the app directory: the new generated file makes it build again.
- `src/hono/extensions.ts` (in `/hono`): `defineExtension()` and `mergeBindings()`. A module has a function for each phase (`EXTENSION_PHASES`: `middleware`, `beforeFiles`, `afterFiles`); a function in place of the object is the `middleware` phase. The app calls `mergeBindings()` at the top level, so that a bad module (not `defineExtension()`, bad phases) or a binding conflict stops the build (Wizer). Then it runs the `middleware` phase of all modules, then their `beforeFiles` phase, `serveStatic()`, and their `afterFiles` phase, each in file-name order. `BindingResource` types `c.env` in a module from its bindings, with `| undefined`, and without a dependency on `@fastly/hono-fastly-compute`.
- `template init` (`commands/manage/template/`, `managed/template-init.ts`) makes or updates the folder from `resources/template-init/<template>/`. The template owns only the peer dependencies on the provided packages (`providedVersions()`: the template dependencies, from the app's `node_modules` or the template lockfile, and this package). `scaffold` runs it after it writes the project or the app.
- In a managed project, the files of the folder (without `node_modules/` and `.git/`) are part of the fingerprint input (`folderFilesForFingerprint()`).

## The npx command in messages

A message, a help text, or a hint that shows how to run this package uses `cliCommand()` (`util/package.ts`), not the literal `npx @fastly/compute-js-static-publish`. For a prerelease, it adds the dist-tag (`@beta`), because npx without it runs the latest stable version. `cliCommand({ latest: true })` is for the command that makes a new app. The files that the CLI writes into an app, for example the `package.json` scripts of a scaffolded app, keep the command without a dist-tag: the app has this package in its own dependencies.
